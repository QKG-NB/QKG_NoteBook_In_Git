

> **一句话定义**：`CAST_TO` 是 KRL 中用于将变量**序列化**（打包）为原始字节流的指令，本质是一个“内存搬运工”——只负责把变量内存里的 0 和 1 原封不动地复制到字节数组中，不关心这些 0 和 1 代表什么含义。

## 1. 指令含义

- **全称**：**Cast To**（“转换为...”）
    
- **功能**：将一个或多个变量（`REAL`、`INT`、`FRAME`、`AXIS` 等），按其在内存中的原始二进制格式，复制到一个 `CHAR` 数组（字节缓冲区）中。
    
- **通俗理解**：将“数据”变成“字节流”，以便通过 I/O 或网络发送给 PLC 或上位机。
    

## 2. 语法格式

krl

CAST_TO ( Buffer : OUT, Offset : IN, Var1 <, …, Var10> )

|参数|类型|说明|
|---|---|---|
|`Buffer`|`CHAR` 数组|存放打包后字节流的容器（最大 4096 字节）|
|`Offset`|`INT`|开始写入的起始字节位置（**从 0 开始计数**）|
|`Var1...Var10`|任意基本类型|要打包的变量，一条指令**最多 10 个**|

> ⚠️ **重要混淆点**：`Offset` 从 **0** 开始，而数组下标 `Bytes[1]` 从 **1** 开始，两者是独立的！
> 
> `Offset = 0` → 从数组的第 1 个元素（`Bytes[1]`）开始写入。  
> `Offset = 4` → 从数组的第 5 个元素（`Bytes[5]`）开始写入。

## 3. 各类型占用的字节数

|数据类型|字节数|说明|
|---|---|---|
|`INT`, `REAL`, `ENUM`|4|标准 32 位|
|`BOOL`, `CHAR`, `BYTE`|1|单字节|
|`FRAME`|24|6 个 `REAL`（X,Y,Z,A,B,C）|
|`AXIS`, `POS`|24|6 个 `REAL`（A1~A6）|
|`E6POS`|48|6 个 `REAL` + 6 个状态/转角值|

## 4. 不同数据类型在内存中的编码规则（核心！）

### 🔢 4.1 `INT`（整数）→ 二进制补码

**规则**：直接存储该数值的十六进制形式（负数用补码）。  
**不遵循 IEEE 754！**

|数值|大端十六进制|小端（库卡内存实际存储）|
|---|---|---|
|`1234`|`00 00 04 D2`|`D2 04 00 00`|
|`-1234`|`FF FF FB 2E`|`2E FB FF FF`|
|`1`|`00 00 00 01`|`01 00 00 00`|
|`-1`|`FF FF FF FF`|`FF FF FF FF`|

**负数补码计算口诀**：先算正数的十六进制，然后“取反 + 1”。

#### 手算示例：`-1234` 是怎么来的？

|步骤|操作|结果|
|---|---|---|
|①|`1234` 的十六进制|`00 00 04 D2`|
|②|按位取反（0变1，1变0）|`FF FF FB 2D`|
|③|加 1|`FF FF FB 2E`|

所以 `-1234` 的大端十六进制就是 `FF FF FB 2E`，库卡小端存为 `2E FB FF FF`。

---

### 🔬 4.2 `REAL`（浮点数）→ IEEE 754 标准

**规则**：遵循 IEEE 754 32位单精度浮点数标准。  
**不存直接的十六进制数值！**

32 位浮点数由三部分组成：

|位数|名称|作用|
|---|---|---|
|**第1位**|**符号位 S**|0 正 1 负|
|**第2~9位**（共8位）|**指数位 E**|存储时加了偏移量（+127）|
|**第10~32位**（共23位）|**尾数位 M**|存的是小数点后的纯小数部分|

计算公式：**`(-1)^S × 1.M × 2^(E-127)`**

#### 手算示例：浮点数 `45.678` 是怎么存成 `42 36 6B 9E` 的？

|步骤|操作|结果|
|---|---|---|
|①|十进制转二进制|`45.678` ≈ `101101.100110...`|
|②|科学计数法|`1.011011001101... × 2^5`|
|③|符号位 S|`0`（正数）|
|④|指数 E = 5 + 127|`132` → 二进制 `10000100`|
|⑤|尾数 M（取小数点后23位）|`01101100110101110011110`|
|⑥|拼装成大端|`0100 0010 0011 0110 0110 1011 1001 1110` = `42 36 6B 9E`|

---

### 📝 4.3 `CHAR`（字符）→ ASCII 码

**规则**：直接存储该字符的 ASCII 码数值（1 个字节）。

|字符|ASCII 码（十进制）|十六进制|
|---|---|---|
|`'A'`|65|`0x41`|
|`'B'`|66|`0x42`|
|`'0'`（数字字符）|48|`0x30`|
|空格 `' '`|32|`0x20`|

> ⚠️ **重要**：`CAST_TO` 不支持 `STRING` 类型。如想发送文本字符串，请用 `CWRITE` 直接发送。

## 5. 字节序（Endianness）—— 数据在内存中的排列顺序

KUKA KRC4 控制器采用**小端（Little-Endian）**存储：

- **低位字节放在低地址（数组前面）**
    
- **高位字节放在高地址（数组后面）**
    

### 示例：`Robot_A1 = 45.678`（`REAL`）

内存中（小端）存储为：`9E 6B 36 42`

|数组索引|存储内容|说明|
|---|---|---|
|`Bytes[1]`|`0x9E`|最低字节（LSB）|
|`Bytes[2]`|`0x6B`|次低字节|
|`Bytes[3]`|`0x36`|次高字节|
|`Bytes[4]`|`0x42`|最高字节（MSB）|

如果要以**大端（高位在前）**发送给 PLC，需要手动反转顺序：

krl

A1_1 = Bytes[4]   ; MSB
A1_2 = Bytes[3]
A1_3 = Bytes[2]
A1_4 = Bytes[1]   ; LSB

## 6. 为什么必须告诉对方数据类型？（协议的重要性）

`CAST_TO` 只负责搬运二进制字节，不关心数据类型。接收方（如 PLC）如果按错误的类型解析，会得到完全错误的结果。

### 🌰 同样的 4 个字节，不同的解读

假设发送的字节（大端顺序）是：`42 36 6B 9E`

|接收方按此类型解析|解析结果|说明|
|---|---|---|
|`REAL`（浮点数）|**`45.678`**|✅ 按 IEEE 754 解析，正确|
|`INT`（有符号整数）|`1111637918`|❌ 得到一个巨大的整数|
|`STRING`（字符串）|`"B6k\x9E"` 乱码|❌ 当成 4 个 ASCII 字符，显示乱码|
|拆成 4 个 `BYTE`|`66, 54, 107, 158`|❌ 分别显示为数值|

### 📝 工程中的标准做法

1. **发送端（机器人）**：必须明确约定并告知接收方“这个字节流代表什么数据类型、什么字节顺序”。
    
2. **接收端（PLC）**：必须按照约定的数据格式，使用对应的功能块去解析。
    

> **协议三要素**：数据长度 + 字节顺序 + 数据类型。三者缺一不可，否则通讯必定出错。

## 7. 代码示例

### 示例 1：将单个 `REAL` 拆成 4 个字节输出

krl

DECL REAL Robot_A1
DECL CHAR Bytes[4]
DECL INT Offset1
Robot_A1 = $AXIS_ACT.A1
Offset1 = 0
CAST_TO(Bytes[], Offset1, Robot_A1)
; 按大端顺序输出到 SIGNAL（8 位端口）
A1_MSB = Bytes[4]   ; 最高字节
A1_2   = Bytes[3]
A1_3   = Bytes[2]
A1_LSB = Bytes[1]   ; 最低字节

### 示例 2：一次性打包整个 `AXIS` 结构体（6 个轴）

krl

DECL AXIS CurrentAxis
DECL CHAR SendBuffer[24]
DECL INT Offset1
CurrentAxis = $AXIS_ACT
Offset1 = 0
CAST_TO(SendBuffer[], Offset1, CurrentAxis)
; 直接通过 CWRITE 发送二进制流
CWRITE($FCT_CALL, Stat, Mode, "EFC_Send", SendBuffer[], Offset1)

### 示例 3：使用偏移量将多个变量打包进同一缓冲区

krl

DECL CHAR AllBytes[16]
DECL INT Offset1
DECL REAL Val1, Val2, Val3, Val4
Offset1 = 0
CAST_TO(AllBytes[], Offset1, Val1)   ; 写入 AllBytes[1..4]
Offset1 = 4
CAST_TO(AllBytes[], Offset1, Val2)   ; 写入 AllBytes[5..8]
Offset1 = 8
CAST_TO(AllBytes[], Offset1, Val3)   ; 写入 AllBytes[9..12]
Offset1 = 12
CAST_TO(AllBytes[], Offset1, Val4)   ; 写入 AllBytes[13..16]

## 8. 常见错误与注意事项

|问题|说明|解决方法|
|---|---|---|
|❌ **数组越界**|`CHAR Bytes[4]` 有效范围是 `Bytes[1]`~`Bytes[4]`|确保访问索引 ≤ 声明的元素个数|
|❌ **数据覆盖**|`Offset` 始终为 0，后面的数据会覆盖前面的|正确计算并更新 `Offset` 值|
|❌ **变量未初始化**|未赋值的变量参与 `CAST_TO` 会写入随机值|使用前先给所有变量赋值|
|❌ **Buffer 赋初值**|在 `.DAT` 中给 `CHAR` 数组赋 `=""` 可能导致错误|声明时不要赋初始值|
|❌ **STRING 类型**|`CAST_TO` 不支持 `STRING` 类型|使用 `CWRITE` 发送字符串|
|✅ **与 CWRITE 配合**|发送字节流时建议使用 `r` 格式|`CWRITE(..., "r", Buffer[], Offset)`|

## 9. 不同数据类型转换速查表

|要打包的对象|占用的字节数|编码标准|有无字节序问题|接收方应如何解析|
|---|---|---|---|---|
|`REAL`（45.678）|4|**IEEE 754** 浮点数|✅ 有（小端）|按 32 位浮点数解析|
|`INT`（1234）|4|**二进制补码**|✅ 有（小端）|按 32 位有符号整数解析|
|`CHAR`（'B'）|1|**ASCII 码**|❌ 无|按 8 位数值接收，也可当 ASCII 字符|
|`BOOL`（TRUE）|1|**0 或 1**|❌ 无|按 1 位或 1 字节布尔值解析|
|`AXIS` / `FRAME`|24|各分量分别按 `REAL` 编码|✅ 有|按结构体逐分量解析|

## 11. 典型应用场景

1. **通过 PROFINET 发送轴角度数据**
    
    - 将 `$AXIS_ACT` 打包后映射到 `SIGNAL` 输出端口
        
2. **EthernetKRL 通讯**
    
    - 配合 `CWRITE` 将字节流发送给上位机或 PLC
        
3. **数据记录与日志**
    
    - 将运行数据打包存储或通过日志输出
        
4. **跨系统数据交换**
    
    - 与第三方设备约定字节序和数据格式进行交换
        

## 12. 快速检查清单

- □ 
    
    确认 `Buffer` 数组大小是否足够（≥ 所有变量总字节数）
    
- □ 
    
    确认 `Offset` 是否正确（从 0 开始）
    
- □ 
    
    确认变量是否已全部初始化
    
- □ 
    
    确认发送端与接收端的**字节序约定**一致
    
- □ 
    
    确认发送端与接收端的**数据类型约定**一致
    
- □ 
    
    确认用 `CWRITE` 发送时使用了 `r` 格式
    
- □ 
    
    确认没有在 `.DAT` 中给 `CHAR` 数组赋初始值
    

## 13. 核心记忆口诀

> **“CAST_TO 是搬运工，只搬字节不解读；**  
> **小端存储是默认，发送大端要反转；**  
> **整数用补码，浮点靠 IEEE；**  
> **数据协议要约定，否则解析全白干！”**

> 📌 **终极理解**：`CAST_TO` 只负责搬运“二进制尸体”，不关心它生前是“数学家（浮点数）”还是“体育生（整数）”。接收方必须提前拿到“尸检报告（数据类型约定）”，才能正确地还原出它生前的身份。
